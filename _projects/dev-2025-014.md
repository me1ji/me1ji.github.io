A session-based home SOC environment built entirely on a portable external drive, combining a working Active Directory domain, a Wazuh SIEM deployment, and a dedicated attacker VM designed around a hard 12GB host RAM budget rather than always-on infrastructure.

## Overview

This lab was built to get hands-on with the full SOC workflow: standing up monitored infrastructure, deploying a SIEM, enrolling endpoints, and eventually generating and detecting real attack traffic. Unlike a typical always-on home lab, every VM here was budgeted against a strict 12GB RAM ceiling, which meant the entire build had to be planned around *sessions* — attack sessions, log-review sessions, domain-admin sessions rather than running everything simultaneously. (I mean if you want to give me a better laptop I'm open to it)

## Objectives

- Stand up a functioning Active Directory domain (`soclab.local`) with a domain controller and a domain-joined endpoint.
- Deploy Wazuh as a centralized SIEM/manager and get its dashboard reliably reachable from the host.
- Enroll Windows endpoints as Wazuh agents and confirm active telemetry.
- Build a dedicated Kali Linux attacker VM, networked to reach lab endpoints without needing internet access on the lab-internal segment.
- Operate the whole environment within a strict RAM budget using a session-based, power-on/power-off workflow instead of an always-on lab.

## Environment and Architecture

The lab runs entirely from a 1TB external WD drive on a Windows host, using VirtualBox as the hypervisor. Four VMs make up the environment:

```text
DC01 (Windows Server, soclab.local)      ─┐
WIN10-ENDPOINT (domain-joined)           ─┼── Internal Network (192.168.56.0/24)
KALI-ATTACKER (Kali Linux)               ─┘         │
                                                    │
WAZUH-MANAGER (Ubuntu Server 24.04) ────────────────┘
        │
        └── NAT (host access via port-forward, e.g. localhost:8443 → 443)
```

<br>

| VM | RAM | Role |
|:-----|:-----:|:-----:|
| DC01 | 2048 MB | Domain controller |
| WIN10-ENDPOINT | 2048 MB | Domain-joined endpoint |
| WAZUH-MANAGER | 4096 MB | SIEM manager + dashboard (bumped up from an original 3072MB plan the indexer and dashboard genuinely needed the extra headroom to install and run reliably) |
| KALI-ATTACKER | 2048 MB | Attacker box |

With all four running simultaneously the host would sit at 10GB+, leaving nothing for the OS itself — not stable on a 12GB budget. The lab instead runs in defined sessions: an attack session (Kali + WIN10-ENDPOINT, ~4GB), a log-review session (Wazuh + whichever machine generated the logs, ~6GB), and a domain-admin session (DC01 + WIN10-ENDPOINT, ~4GB) — powering off whatever isn't actively in use rather than leaving it running in the background.

## Tools

- **VirtualBox:** hypervisor for the entire lab
- **Windows Server 2022:** Active Directory domain controller (DC01)
- **Windows 10:** domain-joined endpoint, Wazuh agent
- **Wazuh 4.9.x:** SIEM manager, indexer, and dashboard (all-in-one install on Ubuntu Server 24.04 LTS)
- **Kali Linux:** dedicated attacker VM
- **NetworkManager (nmcli):** manual static IP configuration on internal-only network segments

## Implementation

### Active Directory domain

DC01 was stood up as a Windows Server 2022 domain controller for `soclab.local`, with WIN10-ENDPOINT joined to the domain as a standard workstation. Both sit on an internal-only VirtualBox network so domain traffic never touches the host's real network.

### Wazuh manager deployment

Wazuh's all-in-one installer was run on a fresh Ubuntu Server 24.04 LTS VM. The install itself surfaced two recurring classes of problem worth documenting:

- **Dashboard unreachable after a "successful" install.** `systemctl status wazuh-dashboard` reported active, but `curl https://localhost:443` refused the connection. `ss -tulnp` confirmed the dashboard process (Node/OpenSearch Dashboards) simply hadn't finished binding its listener yet a timing gap between systemd reporting "Started" and the app actually accepting connections. Waiting it out (or extending `TimeoutStartSec` on the indexer unit) resolved it.
- **"Wazuh dashboard server is not ready yet"** on a later access attempt, which traced to the same root cause a RAM-constrained indexer taking longer than systemd's default timeout to fully initialize before the dashboard could complete its startup handshake with it.

Once resolved, the dashboard was reachable from the host browser via a NAT port-forward rule (host `8443` → guest `443`).

### Agent enrollment

Windows agents for DC01 and WIN10-ENDPOINT were deployed through the dashboard's built-in "Deploy new agent" wizard, which generates a ready-to-run PowerShell install command pointed at the manager's internal IP.

One recurring snag: `Invoke-WebRequest` against `packages.wazuh.com` returned a `403 Forbidden` — most likely upstream bot/WAF protection rejecting PowerShell's default request fingerprint. Switching to Windows' native `curl.exe` (distinct from the `curl` alias to `Invoke-WebRequest`) resolved the download cleanly on the first retry. Both agents installed via `msiexec` and started successfully via `NET START WazuhSvc`, then confirmed **Active** in the dashboard.

### Kali attacker VM

Kali was installed from the standard ISO rather than the prebuilt image, with the installer's primary network interface set to the NAT adapter (needed for package mirror access during install — the internal lab segment has no DHCP and would have stalled the installer). Guided partitioning ("all files in one partition") was used across a 26.8GB disk, keeping the build simple for a single-purpose attack VM.

Post-install, the internal-network interface (`eth0`) had no NetworkManager profile at all only the NAT interface used during install had been configured. A manual profile was created and activated.

```bash
sudo nmcli con add type ethernet ifname eth0 con-name "eth0-internal" \
  ipv4.addresses 192.168.56.40/24 ipv4.method manual
sudo nmcli con up "eth0-internal"
```

A successful ping to the Wazuh manager (`192.168.56.30`) confirmed Kali could reach the internal lab network while retaining internet access via its separate NAT adapter — dual-homed, as intended.

## Challenges

- RAM constraints shaped nearly every infrastructure decision, from Wazuh's memory allocation to the session-based power-on/power-off workflow.
- Startup-timing race conditions (dashboard "not ready" errors) appeared twice during the Wazuh install, both traced back to the indexer needing more time than systemd's default timeout allowed under constrained resources.
- A CDN/WAF-level block on PowerShell's default HTTP client required switching tools (`curl.exe` over `Invoke-WebRequest`) rather than any configuration fix.
- Internal-only network segments have no DHCP by design, which meant every new VM's internal interface needed manual static IP configuration before it could talk to the rest of the lab.

## Current Status

- Active Directory domain operational (DC01 + WIN10-ENDPOINT)
- Wazuh manager, indexer, and dashboard installed and reachable
- Both Windows endpoints enrolled as active Wazuh agents
- Kali attacker VM built, networked, and verified reachable to the lab segment
- Host-Only Adapter networking issue (`VERR_INTNET_FLT_IF_NOT_FOUND`) — worked around via NAT port-forwarding, not yet root-caused

## Lessons Learned

- Patience
- A service reporting "active" in systemd doesn't mean it's actually ready to serve traffic — always verify with a direct connection test, not just service status.
- Tooling-level HTTP client differences (PowerShell's `Invoke-WebRequest` vs. native `curl.exe`) can be the actual fix when a download is blocked, before assuming it's a permissions or network problem.
- Planning a lab around simultaneous RAM budgets rather than assuming "always on" forces clearer session boundaries — and mirrors how a real, resource-constrained SOC has to prioritize what's actively being worked versus idle.
- Internal-only virtual networks need their static addressing planned deliberately from the first VM, so later machines don't collide or get stranded without connectivity.
